# Internationalization and localization: the plan (21 Oct 2026)

A plan, with what is already true and what is not. Counts are from the code on 21 Oct 2026.

## What is true today

- **Time.** Everything stored is UTC (`timestamptz`; the pool's session zone is UTC). "Today" is worked out in one place, `familyos/clock.py`, from a zone kept **in the
  database**: the person's own (`members.timezone`) else the household's (`households.timezone`), bound to each request in `api/deps.py`. `GET/PUT /v1/me/locale` sets it.
  Not yet per household: the recurring sweeps' day (they use the deployment's zone, `settings.timezone`; the digest, the morning message and the nudges already use the
  person's or household's own zone).
- **Language fields exist, nothing reads them yet.** `households.language` (default `en`) and `members.language` (null = the household's), BCP 47 tags, set by
  `PUT /v1/me/locale` and `PUT /v1/household/locale`. Nothing is translated on the strength of them.
- **Country profiles.** `country.py` holds India and the UAE (school-year months, payment rails, currency symbol). Money is shown as `₹1,940.98` or `AED 350`.
- **Reading is already multilingual.** The extractor reads a notice in its own language and keeps its words, quote and title in that language (docs/extraction.md);
  Hindi, Marathi and Nepali digits are handled; voice notes use a Whisper model per language (docs/telegram.md).
- **Everything the product says is English, hard-coded.** The iPhone app has 246 `Text("...")` literals and no string catalog or `.lproj`; the consoles have English
  strings in JS (24 `toLocale…`/`Intl` calls pick up the browser's formats, not the person's); the server writes reminders, the digest, chat cards, Telegram replies and the
  Ask prompts in English; `<html lang="en">` is fixed.

## Principles

1. **The notice's words are never translated by us.** Claims, quotes and titles stay in the notice's language (a translated quote cannot be grounded). A translation, when
   offered, is a separate line labelled as one.
2. **Facts are stored as facts.** Dates ISO, amounts as numbers with an ISO currency, zones as IANA names, languages as BCP 47 tags. Nothing is parsed back out of display text.
3. **Format at the edge, in the person's locale, not the server's.** Number grouping (lakh and crore for `en-IN`, `hi-IN`; thousands elsewhere), dates, times, week start,
   plurals, lists.
4. **Legal and consent text is translated by a person and reviewed**, never by a model alone; a model-translated string is marked as such until reviewed.
5. **Fall back to English, visibly and safely**: an unknown tag or a missing string shows the English string, never a key or an empty screen.

## Phases

0. **Decide the first languages** (founder): English plus Hindi and Tamil for the India profile; Arabic (right-to-left) for the UAE profile is a later phase because it needs layout work.
1. **Foundations (done 21 Oct 2026):** zone and language in the database, `clock.py`, the locale endpoints.
2. **Server catalog.** Message ids and plural-aware templates in `.po` files (Python `gettext`; Babel for extraction and number/date formatting), resolved per recipient from
   `members.language` else `households.language`. Move, in this order: reminders (`reminders.compose`), the digest, the morning message, nudges, Telegram replies,
   chat cards and chips, errors that reach a person. A test fails when a user-facing string is added outside the catalog.
3. **Models.** Ask and the chat prompts say "answer in the member's language, keep names, dates and amounts as written"; cached or staged text records its language.
   Voice: choose the Whisper model by the member's language.
4. **Consoles.** One JSON catalog per language loaded at start; `Intl.DateTimeFormat` and `Intl.NumberFormat` with the member's language and zone;
   `<html lang>` and `dir` set from the language; CSS moved to logical properties (`margin-inline-start`) so right-to-left works; fonts that carry Devanagari, Tamil and Arabic.
5. **iPhone.** A String Catalog (`Localizable.xcstrings`) with `Text(LocalizedStringKey)` for the 246 literals, plural variations, `Locale`-aware formatters, localized
   `Info.plist` usage strings and App Intent phrases, and the notification text from the server catalog. The app follows the member's language setting, not only the phone's.
6. **Formats by country.** Week start and weekend, calendar and holiday packs, phone number and address shapes, names (single names, family-name order), more
   currencies than `SYMBOLS` holds, payment rails by country.
7. **Process.** Pseudo-localization in CI (long, accented, right-to-left) to catch clipping and hard-coded strings; a glossary (school, notice, guardian, consent, family
   key); human review for each language before it is switched on; a per-language switch so a half-translated language is never offered.

## Open questions

- Is a household's language one choice, or does each member pick their own? (The fields allow both; the default is the household's.)
- Do we translate a notice on request ("show me this in English")? It is the one place a model's translation is useful, labelled and never stored as the claim.
- Which languages are in the first release, and who reviews them?
